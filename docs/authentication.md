# Сессионная авторизация

Используются стандартные сессии Django, хранящиеся в PostgreSQL. Пользователи
создаются через Django Admin или команду `createsuperuser`; регистрации пока нет.

## Через браузер

Откройте `/api/auth/login/` и войдите существующим пользователем. В Browsable API
также доступны стандартные ссылки входа и выхода DRF. Для входа не требуется
`is_staff`. После входа `/api/v1/auth/me/` возвращает `id` и `username`.

## Через JSON API

Клиент должен сохранять cookies между запросами.

1. Выполните `GET /api/v1/auth/csrf/`. Ответ содержит `csrf_token` и устанавливает
   cookie `csrftoken`.
2. Выполните `POST /api/v1/auth/login/` с JSON-полями `username` и `password`,
   cookie из первого запроса и заголовком `X-CSRFToken` со значением `csrf_token`.
   При успешном входе сервер вернёт `200`, данные пользователя и cookie `sessionid`.
3. Повторите `GET /api/v1/auth/csrf/`: при входе Django меняет CSRF cookie.
   Используйте новый токен для последующих изменяющих запросов.
4. `GET /api/v1/auth/me/` возвращает текущего пользователя по cookie сессии.
5. `POST /api/v1/auth/logout/` с cookie сессии и актуальным `X-CSRFToken`
   завершает сессию и возвращает `204` без тела ответа.

Неверные данные входа и неактивный пользователь получают одинаковый ответ `403`.
Ошибки обязательных полей возвращаются с кодом `400`. Отсутствующий или неверный
CSRF-токен, недоверенный Origin и обращение к закрытым ручкам без входа возвращают
`403`. GET-запрос на JSON-ручку выхода не завершает сессию и возвращает `405`.

Выход аннулирует сессию на сервере. Смена пароля и деактивация аккаунта также
прекращают доступ по существующей сессии. Ответы ручек авторизации запрещено
кэшировать.
