# Авторизация

API поддерживает JWT в заголовке Authorization и стандартные сессии Django
для Browsable API. Пользователи создаются через Django Admin или команду
`createsuperuser`; регистрации пока нет.

## JWT

1. Выполните `POST /api/v1/auth/token/` с JSON-полями `username` и `password`.
   Ответ `200` содержит `access` и `refresh`. Cookies и CSRF-токен не нужны.
2. Передавайте access в заголовке `Authorization: Bearer <access>` при обращении
   к `/api/v1/tasks/`, комментариям, `/api/v1/users/` и `/api/v1/auth/me/`.
3. Для обновления выполните `POST /api/v1/auth/token/refresh/` с JSON
   `{"refresh": "<refresh>"}`. Ответ содержит новую пару access/refresh.
   Сохраните новый refresh: использованный токен отзывается и повторно не работает.
4. Для выхода выполните `POST /api/v1/auth/token/blacklist/` с JSON
   `{"refresh": "<refresh>"}`. Ответ `200` с пустым JSON-объектом означает,
   что refresh отозван. Клиент также должен удалить свою пару токенов.

Access действует 5 минут, refresh — сутки с момента выпуска или ротации.
Отзыв refresh не аннулирует уже выданный access: он действует до истечения срока.
Деактивация или удаление пользователя блокирует доступ и обновление JWT.
Сессионный `/api/v1/auth/logout/` завершает только сессию, для JWT используется
отдельная ручка blacklist.

Отсутствующий, недействительный или истёкший JWT возвращает `401`, а запрет
действия авторизованному пользователю — `403`. JWT проверяется первым: неверный
Bearer не заменяется существующей сессией. В Swagger UI можно указать access
через кнопку Authorize. Схема безопасности — `jwtAuth`.

При первом запуске после обновления примените миграции blacklist:

```bash
poetry run python manage.py migrate
```

Просроченные записи outstanding/blacklist можно очищать командой:

```bash
poetry run python manage.py flushexpiredtokens
```

## Сессия через браузер

Откройте `/api/auth/login/` и войдите существующим пользователем. В Browsable API
также доступны стандартные ссылки входа и выхода DRF. Для входа не требуется
`is_staff`. После входа `/api/v1/auth/me/` возвращает `id` и `username`.

## Сессия через JSON API

Клиент должен сохранять cookies между запросами.

1. Выполните `GET /api/v1/auth/csrf/`. Ответ содержит `csrf_token` и устанавливает
   cookie `csrftoken`.
2. Выполните `POST /api/v1/auth/login/` с JSON-полями `username` и `password`,
   cookie из первого запроса и заголовком `X-CSRFToken` со значением `csrf_token`.
   При успешном входе сервер вернёт `200`, данные пользователя и cookie `sessionid`.
3. Повторите `GET /api/v1/auth/csrf/`: при входе Django меняет CSRF cookie.
   Используйте новый токен для последующих изменяющих запросов.
4. `GET /api/v1/auth/me/` возвращает текущего пользователя по cookie сессии.
5. `POST /api/v1/auth/logout/` с cookie сессии и актуальным `X-CSRFToken`
   завершает сессию и возвращает `204` без тела ответа.

Неверные данные входа и неактивный пользователь получают одинаковый ответ `403`.
Ошибки обязательных полей возвращаются с кодом `400`. Отсутствующий или неверный
CSRF-токен и недоверенный Origin возвращают `403`. Основные закрытые ручки
без авторизации возвращают `401`; сессионный logout без сессии возвращает `403`.
GET-запрос на JSON-ручку выхода не завершает сессию и возвращает `405`.

Выход аннулирует сессию на сервере. Смена пароля и деактивация аккаунта также
прекращают доступ по существующей сессии. Ответы ручек авторизации запрещено
кэшировать.
